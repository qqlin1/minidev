## 二、用户是谁，怎么跟他讲

**张祥林，学习者/学者，不是熟练工程师。**

他的原话批评过：

> 「你得叙述一点都不完整，很多时候我看到的不是一个完整的场景题，更像是一层半成品……
> 你拿一些术语说的零零散散，我无法完全理解你的意思。」

**必须遵守的讲法（7 条，写在他的 SOUL.md 里）**：

1. **场景自包含** —— 题目里自带全部信息，不假设他记得上文
2. **零指代** —— 不说「它」「上面那个」「前者」
3. **术语首次出现先给现象再给名字**，绝不用术语解释术语
4. **一次只讲一件事**，讲透再往下
5. **要答什么，一条一条编号列出；每条给过关标准**
6. **不省略推导过程** —— 不只给结论，要说清「为什么」
7. **给代码就给完整可粘贴的代码**，不给片段、不给伪代码

**什么有效**：
- 多角色/多步骤的时序**先画图**（`show_widget`），再给代码，最后才给原则
- **实测数据永远优先于解释** —— 写个脚本跑出来给他看，比讲十遍概念有用
- 要他细读或填写的内容，做成**单文件 HTML**（可填 + localStorage + 导出 Markdown + 跟随深浅色）
- 自己的失误**主动讲** —— 他吃这一套，会继续信任而不是质疑

**什么会让他不爽**：
- 术语堆砌、先抛名词再补介绍
- 自造编号（3a / 3b 这种）
- 一次抛一堆新概念把他淹掉

**他的能力在长**：最近他开始**主动质疑已经通过测试的实现**
（「我总感觉先写块再写账本会有一些 bug」「想好了吗」），
而且**提出过比我更好的设计**（文档状态机）。
这种提问要认真对待、变成可复现的实验，**不能用「不会的，我测过了」打发**。

## 四、代码约定（照做，别自创）

**包结构：package-by-feature。** 一个能力一个包，层是包内文件。

```
repo_qa/
  ingest/     models.py  admission.py  loader.py  pipeline.py
  chunking/   models.py  strategies.py  headings.py  config.py  filters.py  pipeline.py
  indexing/   models.py  planner.py  store.py  pipeline.py
  eval/       cases.py  runner.py
```

**依赖方向单向，不成环**：`ingest` 和 `chunking` 互不依赖，`indexing` 依赖前两者。

**每个模块的 docstring 必须写清三件事**：
1. 职责是什么
2. **明确不负责什么**
3. 关键设计决定的**理由**（不是「做了什么」，是「为什么这么做」）

**代码里不写「3a / 3b」这种编号**，用具体场景名
（「事务里跑慢 SQL」/「事务里跑外部接口」）。

**测试**：每个能力都要有正例 + 反例 + 边界。
**修完 bug 必须补回归测试**，并在测试的 docstring 里写清「这个 bug 是什么、为什么会有」。

**数字必须脚本算出来**，不许手数。
（本项目手数行数错过 4 次。）

## 六、已建立的「认知资产」（这些比代码值钱）

1. **静默失败是本项目最贵的坑** —— 踩过 4 次：
   制表符静默降级 / 换行符假更新 / 测试假货假绿 / 账本写了块没写
   → 规则：**凡是「降级」「兜底」「默认值」，都要同时设计「怎么知道它生效了」**

2. **两份数据必须回答两个问题** —— 会不会不一致？不一致怎么发现？
   → 本项目两个 bug 都是「没问过这两个问题」的后果

3. **顺序推理有前提** —— 「先写块后写账本」正确，前提是两份数据持久性一致。
   **前提变了，结论就不成立。**

4. **没有事务时，用「可重跑」替代「原子性」** —— 而「可重跑」的前提是覆盖语义。

5. **对账只抓「意外」，不碰「已知状态」** —— 否则会把 `FAILED` 当丢失剔掉。

6. **让不一致偏向「看得见」的那一侧** —— 这是纵深防御的判据。
